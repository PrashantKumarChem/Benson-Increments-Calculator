# Working on this repository

This file is the working agreement for anyone — person or AI assistant — making
changes here. It covers how work is verified and landed. For what the project is
and how to add increment data, see [`README.md`](README.md); for the contributor
walkthrough, see [`CONTRIBUTING.md`](CONTRIBUTING.md).

The calculator is a teaching tool. Students trust the numbers it shows. That is
the reason for most of the rules below.

Detailed rules for particular areas — the increment data, the browser assets,
the notebook — live in [`.claude/rules/`](.claude/rules/). Claude Code loads
each one automatically when you open a file it covers. **If your tool does not
read that directory, read the relevant file yourself before working in that
area.**

---

## The prime directive

**Verify. Do not assert.**

Never report that something works because it should. Run it, read the output,
and say what actually happened. If a check was skipped, say it was skipped and
why. If a step failed, show the failure.

A confident wrong answer about a chemistry value is worse than no answer.

---

## Before changing anything

Read the part of the codebase you are about to touch, not just the documentation
describing it. Documentation drifts; the code is what runs. Where the two
disagree, the code is the fact and the documentation is a bug.

If an untracked `Plan/` directory is present, read `Plan/README.md` first — it
holds the current architecture and roadmap.

---

## Running the site

The site is plain HTML, CSS and JavaScript with no build step. It must be
**served** rather than opened from disk, because browsers block a `file://` page
from reading the CSV data:

```bash
python -m http.server 8000     # then open http://localhost:8000/
```

## The checks

All of these must pass before and after every change:

```bash
python tools/build_version.py     # regenerates the asset hash; CI fails on a diff
python tools/validate_data.py     # the increment CSVs and the manifest
python tools/validate_assets.py   # every asset requested at one version
node   tools/validate_css.mjs     # the stylesheet parses; every token exists
node --test tools/*.test.mjs      # unit tests
python -m unittest discover -s benson/tests -t .   # the benson package's tests
node   tools/check_parity.mjs     # every increment: notebook vs. site
node   tools/check_render.mjs     # the page, in a real browser
```

Notes:

- **Never assert a specific test count.** It grows. Assert zero failures.
  Read `unittest`'s count all the same: before Python 3.12 it reports `OK`
  having found no tests at all.
- `check_parity.mjs` needs a `PYTHON` environment variable pointing at an
  interpreter with `pandas`.
- `check_render.mjs` is the only check needing a browser:
  `npm install --no-save playwright && npx playwright install chromium`.
  Install it outside the repository so nothing here is polluted.

If you cannot run a check, say so explicitly and name which one. Do not imply
coverage you do not have.

---

## A check that has never failed is not a check

When you add a test, a validator rule, or a guard, **prove it fails.** Break the
thing it protects, watch it go red, confirm the message names the actual rule
rather than an incidental error, then restore.

This is not ceremony. Tests that silently assert nothing have been caught here
more than once, and a validator rule that fires on the wrong condition is worse
than none — it teaches contributors to distrust the tooling.

---

## Generated files are never hand-edited

| File | Generated by |
|---|---|
| `CSV_data_files/manifest.json` | `tools/build_data.py` |
| the asset version in `index.html` | `tools/build_version.py` |

Regenerate them; commit the result. CI regenerates independently and fails if
the committed copy differs. Hand-editing one produces a change that passes
locally and fails in CI, or worse, passes both and is wrong.

## Code conventions

Match the surrounding code.

- **Comments explain *why*, not *what*.** The code says what it does. A comment
  earns its place by recording the reason, the constraint, or the failure that
  produced the design.
- Prefer a rule expressed once as data over the same rule written twice in two
  languages.

---

## Branches, commits and pull requests

- **Never commit to the default branch.** Branch first.
- **One concern per pull request.** A change that fixes a bug and also
  reorganises a module is two pull requests. Reviewers cannot separate them
  afterwards, and neither can `git revert`.
- Do not do adjacent work you noticed along the way. Note it and move on;
  scope creep is how a reviewable change becomes an unreviewable one.
- Write commit messages that record *why*. The diff already shows what.
- If you must leave work incomplete, say exactly what is done, what is not, and
  what the next step is.

---

## Privacy

**Never commit a machine-specific path, username, home directory, or machine
name.** Not in code, not in documentation, not in a comment, not in a commit
message. This repository is public.

Local settings — an interpreter path, an environment variable — belong in an
untracked file.

---

## When you are unsure

Ask, or write down the assumption you are proceeding on and mark it as one.

Two things in particular are not an assistant's call to make:

- **A chemistry judgement.** Whether a value is right, whether a correction
  applies, whether an entry should exist. Raise it with the evidence.
- **Anything about licensing, permissions, or publication.** Flag it; do not
  resolve it.

Guessing at either produces something that looks authoritative and is not, which
is the specific failure this project cannot afford.
